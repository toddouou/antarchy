# R2 Class-A Optimization Plan — Snapshot Writes

> **2026-06-04.** Companion to [`EGRESS_PLAN.md`](./EGRESS_PLAN.md) (Phase-6 R2 snapshot pipeline).
> Scope: reduce **Cloudflare R2 Class-A operations** (`PutObject` per dirty chunk) generated by the
> snapshot-writer thread (`src/server.rs::snapshot_writer_loop`). Written standalone-executable: a
> future agent with no memory of this session can run any phase from this doc + the code.
>
> **Decision (operator, 2026-06-04):** ship all three levers together —
> **(A)** tunable writer interval, **(B)** coarser PNG tiles, **(C)** pay the residual.
> Accepted ceiling: **~$200/yr worst case** (see §Budget).

---

## 0. The finding (why this is the whole problem)

Measured: a **4-player, 6-hour** playtest produced **~8.1k Class-A ops** (Class-B reads only 629).
Class-A is driven entirely by `PutObject` — one per **dirty 256×256 chunk per writer cycle**
(`server.rs:681-685`). `DeleteObject` is **free** on R2 (neither class), so the `Empty→delete` branch
and wipe-cleanup cost nothing.

```
6 h ÷ 90 s interval        = 240 writer cycles
8,100 puts ÷ 240 cycles    ≈ 34 dirty chunks / cycle (4 players)
```

**Two things are already optimal — do not re-attempt them:**

1. **No-op repaints are free.** `TileMap::set` early-returns *before* `note_dirty` when the owner is
   unchanged (`tile_map.rs:242`, `:253`). Brutes repainting their own footprint, ants crossing their
   own solid territory — none of it dirties a chunk. The dirty set is **owner-change-precise**.
2. **The dirty set dedupes per interval.** `drain_dirty_chunks` returns a `HashSet` drain
   (`tile_map.rs:155`). A chunk that flips 1,000× inside one window still drains as **one key = one
   put**. Content-hashing the PNGs would add ~nothing.

So the cost decomposes into two regimes — this is the governing insight:

| Regime | Source | Cost over a window | Interval helps? |
|---|---|---|---|
| **Oscillating frontier** | contested border, same chunks flip-flop | `K_chunks × cycles` | **Yes, linear** |
| **Advancing frontier** | painting into fresh land, new chunks each cycle | `≈ chunks_painted` (interval-independent) | **No** |

**The irreducible floor** = ~**one PutObject per chunk that ever changes owner**. To persist a canvas
of `N` painted cells once costs `N / 65,536` puts minimum (65,536 = cells per 256×256 chunk). At the
target ~100 B painted cells/season that's **~1.5 M puts just to lay down the final canvas once** —
already past the 1 M/mo free cap before any re-settling. **No amount of interval tuning removes this
floor; only coarser tiles attack it, and the rest is cheap enough to pay.** Hence all three levers.

## Budget — the $200/yr ceiling

R2 pricing (**re-verified 2026-06-04** against the official R2 pricing docs + a direct Cloudflare
support reply): **Class-A = $4.50 / million ops**, **1 M/mo free**; Class-B = $0.36/M, 10 M/mo free;
storage $0.015/GB-mo (10 GB free); **egress $0**; **`DeleteObject` and abort-multipart are free**
(neither class). Class-A = writes/copies/**LIST**/multipart-init; Class-B = reads/HEAD.

> ⚠️ Correction to an earlier verbal estimate in this session: Class-A is **$4.50/M**, not $0.18/M.
> The operator's independent "~$200/yr worst case" is the figure to trust.
>
> ⚠️ **Do NOT switch to the Infrequent-Access storage class to save money.** IA *doubles* Class-A to
> **$9.00/M** (and Class-B to $0.90/M) and adds a $0.01/GB retrieval fee + 30-day minimum. This
> workload is **Class-A-bound, not storage-bound**, so IA is strictly worse here. Stay on Standard.

`$200/yr ÷ $4.50/M ≈ 44 M billable ops/yr ≈ 3.7 M billable/mo` → ~**4.7 M Class-A/mo sustained**
(after the 1 M free) is the accepted ceiling. Levers A+B aim to keep **typical** production usage
*under* that; **C** absorbs spikes (busy seasons, all-four-corners activity) without a code change.

**Acceptance:** with A (300 s) + B (1024 px tiles) shipped, a 4-player playtest should land **well
under 1 M/mo** (free tier), and the projected production worst case should sit **≤ ~5 M/mo**
(≤ ~$200/yr). Validate against `/egress-stats` dirty-chunk counters (§Measurement).

## Phase A — Tunable writer interval  *(Lever 1; trivial; kills the oscillating regime)*

**Goal:** make the hardcoded `Duration::from_secs(90)` (`server.rs:637`) an env knob so the operator
dials Class-A vs. cold-load freshness with **zero rebuild**. Longer interval → fewer cycles → linear
cut of the oscillating-frontier cost. Only downside: snapshot tiles up to `interval` seconds stale on
cold-load / reconnect — **acceptable**, because the live in-view canvas is WS-keyframe-authoritative
(`drawSnapshotTiles` only paints *before the first live frame*, `client.html:2566-2570`).

### A1. Add the env reader (`src/config.rs`, beside `snapshot_dir`/`snapshot_cdn_enabled`)
```rust
/// Phase-6 snapshot-writer cadence in seconds (R2 Class-A lever). `HIVE_SNAP_INTERVAL_SECS`,
/// default 300, clamped to [30, 3600]. Longer = fewer PutObject ops, staler cold-load tiles
/// (the live view is WS-authoritative, so staleness only affects pre-first-frame paint). Read once.
pub fn snapshot_interval_secs() -> u64 {
    static V: OnceLock<u64> = OnceLock::new();
    *V.get_or_init(|| {
        std::env::var("HIVE_SNAP_INTERVAL_SECS").ok()
            .and_then(|s| s.trim().parse::<u64>().ok())
            .unwrap_or(300)
            .clamp(30, 3600)
    })
}
```

### A2. Use it (`src/server.rs::snapshot_writer_loop`, ~line 636)
```rust
let secs = crate::config::snapshot_interval_secs();
let interval = Duration::from_secs(secs);
println!("[snapshot] writer started (sink: {}, interval {secs}s)", sink.label());
```

**Default bump 90 → 300 s** is the recommendation (≈3.3× off the oscillating component). Keep 90 s
only if cold-load tile freshness is observably bad in playtests.

**Effort:** ~10 min, server-only, no client change. **Risk:** none beyond cold-load staleness.

## Phase B — Coarser PNG tiles (super-tiles)  *(Lever 2; attacks the floor)*

**Goal:** one PNG per **S×S block of chunks** instead of per single chunk. With `S = 4` →
**1024×1024** PNGs, each key covers 16 chunks. When a player's (contiguous) frontier dirties several
sub-chunks of the same block in one window, they collapse to **one** put — up to **16× fewer keys**
where activity clusters (realistically ~4–8× for a sweeping frontier; ~1× for scattered lone trails).
This is the only lever that reduces the *advancing-frontier floor*.

**Trade-offs (state them honestly):**
- Each PNG is 16× larger to encode (transient 4 MB RGBA buffer on the writer thread, one at a time —
  fine) and 16× larger on cold-load fetch (**egress is $0**, so this is bytes/CPU, not billed).
- A super-tile re-uploads if **any** of its 16 sub-chunks dirtied → a 1-chunk change can re-push a
  16× tile. Net win therefore depends on **spatial clustering**; Langton territory is contiguous per
  queen, so it clusters well. **`S` is tunable so the win is measurable, not assumed.**

### B0. Make `S` an env knob (`src/config.rs`)
```rust
/// Phase-6 super-tile factor: each snapshot PNG covers S×S native chunks (S×256 px square).
/// `HIVE_SNAP_TILE_CHUNKS`, default 4 (→1024 px), restricted to {1,2,4,8}. Higher = fewer
/// Class-A keys when activity clusters, larger PNGs. MUST be sent to the client (see B3). Read once.
pub fn snapshot_tile_chunks() -> u32 {
    static V: OnceLock<u32> = OnceLock::new();
    *V.get_or_init(|| {
        let s = std::env::var("HIVE_SNAP_TILE_CHUNKS").ok()
            .and_then(|s| s.trim().parse::<u32>().ok()).unwrap_or(4);
        if [1, 2, 4, 8].contains(&s) { s } else { 4 }
    })
}
```

### B1. Coalesce dirty chunks → super-tiles, rasterize a block (`src/snapshot.rs`)
Replace the per-chunk capture/rasterize with a per-super-tile one. Sketch:

- **`supertile_key(cx, cy, s) -> (u32, u32)`** = `(cx / s, cy / s)` (s is power-of-two → `>> log2 s`).
- **`snapshot_supertile(tiles, sx, sy, s) -> SuperSnap`**: under the read lock, capture all `s*s`
  constituent chunks (`view_chunk` each; `None` → transparent). Mark `AllEmpty` iff every constituent
  chunk is empty (→ the super-tile is deleted, free op); otherwise capture owner-id cells per
  sub-chunk for off-lock rasterization.
- **`rasterize_supertile(snap, colors, s) -> Vec<u8>`**: allocate one `(s*256)²` RGBA buffer; blit
  each sub-chunk at pixel offset `(scx*256, scy*256)`; encode one PNG. Reuse `parse_hex_color` /
  per-cell `put`. Transparent (α=0) for unclaimed/ocean cells — byte size still tracks painted
  perimeter.

### B2. Writer loop drives super-tiles (`src/server.rs::snapshot_writer_loop`)
- After `drain_dirty_chunks()`, **map each dirty chunk key → its super-tile key** and dedup into a
  `HashSet<(u32,u32)>` (this is where the Class-A reduction happens).
- Phase A2 (read lock): `snapshot_supertile` for each dirty super-tile.
- Phase B (no lock): key = `format!("snap/{epoch}/0/{sx}/{sy}.png")` (same path shape; `(sx,sy)` is now
  super-tile index, not chunk index — client matches via B3). `AllEmpty → sink.delete` (free),
  else `sink.put`. Keep the `uploaded/deleted/failed` tally + log.
- **Wipe cleanup (`delete_prefix snap/{old}/`) is unchanged** — it nukes the whole epoch regardless of
  tiling, and `DeleteObject` is free.

### B3. Client must learn the tile span (`src/network.rs` + `public/client.html`)
The client currently hardcodes `SNAP_CHUNK=256` (`client.html:1254`) and keys
`snap/${epoch}/0/${cx}/${cy}.png` with `cx=floor(gx/SNAP_CHUNK)` (`client.html:2574`, `:2558`). Make
the span **server-provided** so server `S` and client never desync:

- **Server:** wherever `snapshotBase`/`epoch` are placed into the `logged-in`/`me` payload and
  `world-info` (see `network.rs:194` for `epoch`, and `client.html:1809-1810` for the read sites), add
  `snapTileCells = snapshot_tile_chunks() * 256` (e.g. `1024`).
- **Client:** replace `const SNAP_CHUNK=256;` with a `let SNAP_CHUNK=256;` updated from
  `me.snapTileCells` (fallback 256 when absent → backward-compatible with an un-upgraded server). The
  rest of `drawSnapshotTiles` already works in game-space units: bigger `SNAP_CHUNK` just means fewer,
  larger `drawImage` calls; `(cx,cy)` computed as `floor(gx/SNAP_CHUNK)` equals the server's `(sx,sy)`.
  Bump the loop guard (`>400`) proportionally (a 1024 px tile covers 16× the area → `>64` is
  equivalent), and the `snapCache` LRU size is fine.

> **Epoch cache-bust covers the migration:** changing `S` does **not** auto-roll the epoch, so old
> 256 px tiles under the live epoch would 404 against the new `(sx,sy)` keys until re-uploaded. Two
> safe options: **(a)** roll the epoch once when `S` changes (cleanest — `fresh_epoch` on boot if the
> stored tiling tag differs), or **(b)** accept a brief cold-load gap as super-tiles re-upload over the
> first interval (the WS path fills the live view meanwhile). **Recommend (a)**: persist the active
> `S` and call `rotate_epoch_retiring_old()` on mismatch so the stale generation is reclaimed.

**Effort:** ~half a day (server rasterizer + writer coalescing + client constant + one payload field +
epoch-on-tiling-change). **Client recompile required** (`include_str!`). **Risk:** medium —
verify with the local-disk sink (`HIVE_SNAP_DIR`) before pointing at R2; eyeball a 1024 px PNG and
confirm the client composites it aligned (no half-chunk offset).

## Phase C — Pay the residual  *(Lever 3; zero code)*

After A+B, whatever Class-A remains is the genuine cost of persisting a planet-scale canvas. **Do not
engineer past it** — it's cents-to-low-dollars:

1. **Enable R2 paid usage** on the Cloudflare account (removes the 1 M/mo hard stop; billed at
   $4.50/M beyond free). No code, no flag.
2. **Set a billing alert / budget** at the ~$200/yr (~$17/mo) ceiling so a runaway (e.g. a stuck
   oscillation bug re-pushing the same blocks) is caught by alert, not by a surprise invoice.
3. **Leave `delete`/`delete_prefix` as-is** — deletes are free and keep storage (the $0.015/GB-mo
   line) tracking live territory.

## Considered & rejected (so a future agent doesn't re-derive these)

A 2026-06-04 sweep of current R2 cost-reduction best practice surfaced these alternatives. The two
"first moves" everyone recommends — **only write on change** and **debounce/batch rapid edits** — are
*already* implemented here (owner-change-precise dirty set + per-interval `HashSet` dedup, §0), which
is why A+B+C is what's left. The heavier options were evaluated and rejected:

- **Object-packing: many chunks → one <100 MB blob + index file + HTTP range requests.** The logical
  extreme of batching (a Medium write-up pegs it as ~3 orders of magnitude cheaper on Class-A). The
  fatal cost here: it **breaks the browser's direct tile fetch** (`snap/{epoch}/0/{cx}/{cy}.png`),
  which is the entire reason we're on R2 for **$0 egress**. It would force an index, range-request
  client logic, and likely a Worker to maintain the index. **Super-tiles (Lever B) are the same
  "batch into bigger objects" idea at ~5% of the complexity, and keep direct fetch intact.** Revisit
  *only* if post-launch `/egress-stats` telemetry shows Class-A genuinely blowing past the $200/yr
  ceiling — the §0 floor math says it won't once S=4 ships.
- **Cloudflare Worker / Durable Object write-buffer.** The standard "buffer in a Worker, flush every
  5–60 s" pattern. We already *are* that buffer: the single snapshot-writer thread with the §A
  interval **is** the flush window. No win for an extra moving part.
- **Infrequent-Access storage class.** Rejected — see the Budget ⚠️ (doubles Class-A; we're
  Class-A-bound).

**Bonus from Lever B not previously noted:** coarser tiles also cut **Class-B** — cold-load fetches
16× fewer GETs per area (one super-tile vs. 16 chunk tiles). Class-B is cheap (10 M free) so it's not
the bottleneck, but it's a free reduction in request count / connection overhead.

## Measurement & acceptance

Use the existing instrumentation — **no live-server disruption** (operator runs prod on :8080; test on
:8090, `CARGO_TARGET_DIR=target-dev`):

- **`/egress-stats`** already exposes `dirty_chunk_touches` (cumulative) and `dirty_chunk_len`
  (pending). **Projected Class-A/mo ≈ (distinct super-tiles per interval) × (intervals/mo).** After B,
  add a `dirty_supertiles_len` gauge (coalesced count) so the projection reflects the real key count.
- **Writer log** (`server.rs:693`) prints `uploaded/deleted/failed` per cycle — watch `uploaded`
  (= Class-A puts/cycle) drop after A (longer interval → counted per-cycle, fewer cycles) and after B
  (fewer keys/cycle).
- **Gate:** 4-player playtest projects **< 1 M Class-A/mo** (free tier). Production worst-case
  projects **≤ ~5 M/mo** (≤ ~$200/yr). Confirm a 1024 px tile renders correctly client-side.
- **Cross-check on Cloudflare:** the R2 dashboard's Class-A counter over a fixed playtest window
  vs. the summed `uploaded` from the writer log — they should match.

## Invariants to preserve (don't regress)

- `DeleteObject` stays the `Empty`/wipe path (free) — never convert deletes to puts.
- **`ListObjects` is Class-A.** The only LIST in the pipeline is `delete_prefix`'s epoch enumeration
  on a wipe (`snapshot.rs:204`, ~1 op / 1,000 keys) — rare and tiny, so it's ignorable. But **never
  add a routine/per-cycle LIST** (e.g. to "check what exists" before writing); the owner-change dirty
  set already tells the writer exactly what to push without listing.
- Snapshot tiles only paint **pre-first-live-frame** (`drawSnapshotTiles`); never let a stale R2 tile
  bleed into the authoritative live overlay.
- `S` is power-of-two and identical on server (`snapshot_tile_chunks`) and client (`snapTileCells`) —
  drive it from one server-sent field.
- Wipe still rolls the epoch + queues `snap/{old}/` for `delete_prefix` reclamation
  (`rotate_epoch_retiring_old`, `world.rs:327`).
